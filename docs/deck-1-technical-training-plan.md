## Slide 3 — Branch 1: Conversation Mode
### `week-4/conversation-mode` — `eva` + `eva-mobile`

**What it is:** Full duplex voice conversation. Driver speaks, EVA listens continuously via OpenAI Realtime API, transcription is live in chat, EVA responds with streaming TTS. Barge-in supported.

**What it lives in:**
- `eva`: `apps/server/src/voice/realtime-asr.ts`, `session/session-manager.ts`, `voice/tts.ts`
- `eva-mobile`: `src/lib/audio.ts`, `src/screens/ChatScreen.tsx`, `src/lib/ws-client.ts`

**Key engineering problems:**
- OpenAI Realtime API transcription-only session (`type: "transcription"` in `session.update`)
- Server VAD or Semantic VAD for natural turn detection
- Streaming MP3 chunks from ElevenLabs while LLM is still reasoning
- Barge-in: interrupt TTS + discard stale reasoning when driver starts talking again
- TurnVersion to prevent stale audio playback

**Training / fine-tuning angle:**
- Not applicable for conversation mode itself
- But this branch produces the audio + transcript data pipeline that feeds fine-tuning datasets later

**Dependencies:** `OPENAI_API_KEY` (realtime), `ELEVENLABS_API_KEY` (streaming)

**Can be delegated:** Yes. Design docs in branch. Mobile and server must be worked together.

**Acceptance criteria:**
- Driver speaks → transcript appears in chat within 500ms of end of utterance
- EVA responds in voice within 2s of turn end
- Barge-in cancels audio playback immediately
- No AI audio response generated by the realtime model (transcription-only)

## Slide 4 — Branch 2: Active Inference Engine
### `feature/active-inference-engine` — `eva` only

**What it is:** The engine that infers driver state, selects persona, suggests mode, and enriches the system prompt on every turn. Built on 5 silos: ADAS, driver input, memory tier, environment, inferences.

**What it lives in:**
- `apps/server/src/inference/` (new module)
- `packages/types/src/inference.ts` (new types)
- `infra/supabase/migrations/006_inferences.sql` (new table)
- `apps/server/src/personas/base.ts` (updated to read from inference output)

**Key engineering problems:**
- Silo snapshot — assembling a consistent view of all 5 silos each turn without blocking the response
- Path registry — configurable, versioned inference paths that can be added/tuned without redeployment
- Confidence model — how is per-path confidence computed and how does it decay
- System prompt injection — injecting driver state vector as natural language hints without overfilling the prompt
- Persona selector — mapping inferred state + mode to the correct persona block

**Where fine-tuned GPT-4o mini fits:**
The fine-tuned mini is a **component inside this engine** — it replaces rule-based logic in specific paths (driver input signal extraction, intent classification). It is NOT the main reasoning model.

Architecture when mini is deployed:

```
Every turn:
  1. Fine-tuned gpt-4o-mini classifies:
     - Driver intent from utterance
     - Fatigue/stress signals from transcript text
     - Preference cues from conversation
     Output: structured JSON (low latency, cheap)

  2. AIS inference engine runs paths:
     - Reads silo snapshots including mini output
     - Emits driver state vector + persona recommendation

  3. Persona selector picks persona block

  4. Claude Sonnet receives enriched system prompt with:
     - Driver state vector
     - Recommended persona
     - Memory retrieval
     - Mode context
     → Reasons and responds
```

**Training / fine-tuning angle:**
- The AIS engine itself is not trained — it is rule-based + mini-assisted
- The mini model IS trained (see Branch 3)
- Tiered memory matrix (see Slide 7) feeds this engine via Silo 3
- ADAS interpreter feeds this engine via Silo 1

**Can be delegated:** Yes, mostly. Persona selector and system prompt injection require deep understanding of the existing prompt structure — best done with OpenCode. Path implementations can be delegated.

## Slide 5 — Branch 3: Prompt Engineering + Fine-Tuning
### `feature/prompt-engineering` — `eva` only

**What it is:** Two workstreams in one branch:

**A. Prompt engineering for Claude**
Extended persona prompts for `coach`, `discoverer`, `briefer`, `dispatcher`. Prompt evaluation harness. Style-anchoring examples per persona.

**Lives in:**
- `apps/server/src/personas/coach.ts` (new)
- `apps/server/src/personas/discoverer.ts` (new)
- `apps/server/src/personas/briefer.ts` (new)
- `apps/server/src/personas/dispatcher.ts` (new)
- `apps/server/src/__tests__/persona-eval.ts` (new eval harness)

**B. Fine-tuning GPT-4o mini**
Train a specialist model for the AIS driver input path. Not replacing Claude — enriching the context Claude receives.

**Training platform:** OpenAI fine-tuning API
- Dataset format: JSONL, `{"messages": [{role, content}, ...]}` format
- Training data source: curated conversation turns from EVA sessions + synthetic examples
- Job trigger: `POST /v1/fine-tuning/jobs` with your `gpt-4o-mini` base model
- Result: a model ID you plug into `OPENAI_REALTIME_MODEL` or a new env var `OPENAI_MINI_MODEL_ID`

**What the mini is trained to do:**
1. **Intent classification** — given a driver utterance, classify: `navigation_request`, `vehicle_query`, `wellbeing_signal`, `feedback`, `small_talk`, `emergency`
2. **Fatigue/stress signal extraction** — given a transcript, return: `{hedgeDensity, terseness, speechRateEstimate, frustrationMarkers[]}`
3. **Preference extraction** — given a conversation turn, return: `{preferenceDetected: bool, category: string, value: string, confidence: float}`

**Training data requirements (minimum viable):**
- ~100 curated examples per task (300 total minimum)
- Balanced across driver states, modes, edge cases
- Safety examples (refusals, edge cases handled correctly)
- Export script: `scripts/export-finetune-dataset.ts` — queries Supabase for approved turns, formats as JSONL

**Demo capability this unlocks:**
Show side-by-side: base `gpt-4o-mini` vs fine-tuned EVA mini given the same driver utterance. Fine-tuned version correctly identifies intent and fatigue signals. Demonstrates understanding of fine-tuning as a tool, not a magic fix.

**Works in:** OpenCode for prompt files. OpenAI Playground + API for fine-tuning jobs. No GPU needed.

## Slide 6 — Branch 4: Tiered Memory Tuning
### `tweak/tiered-memory` — `eva` only

**What it is:** Adjusting the parameters, thresholds, and extractor prompts of the existing tiered memory system. Not structural changes — tuning the engine that already runs.

**What it lives in:**
- `apps/server/src/memory/extractor/categories.ts` — confidence thresholds, promotion rules
- `apps/server/src/memory/extractor/extract.ts` — extractor system prompt
- `apps/server/src/memory/analyser/session-analyser.ts` — Tier 3 pattern detection logic
- `apps/server/src/memory/extractor/confirmation-queue.ts` — confirmation question templates

**What tiered memory also touches in AIS:**
The memory tier is Silo 3 of the inference engine. As the AIS is built, memory tier tuning will include:
- New category: `inferred_state_pattern` — patterns from the inference engine promoted to confirmed memory
- New source type: `inference` — memory candidates generated by the AIS paths
- New retention rules for inference-sourced candidates

**Can be delegated:** Yes. Small PRs, fast merge cycle. No mobile changes.

**Short-lived branch:** Create, tweak, test, merge back to main. Repeat.

## Slide 7 — How the Branches Relate

```
conversation-mode ──────────────────────────────────► main
  Produces: audio/transcript data pipeline
  Feeds: fine-tuning dataset (later)

prompt-engineering ─────────────────────────────────► main
  Produces: persona prompts + fine-tuned mini model
  Feeds: active-inference-engine (mini becomes AIS component)

active-inference-engine ────────────────────────────► main
  Consumes: memory tier (Silo 3) + ADAS (Silo 1)
  Consumes: fine-tuned mini output (Silo 2)
  Produces: driver state vector → persona selection → enriched prompt

tweak/tiered-memory ────────────────────────────────► main
  Tunes: memory tier parameters
  Feeds: active-inference-engine (Silo 3 data quality)
```

Order of operations:
1. **Prompt engineering** can start now — no dependencies
2. **Tiered memory tuning** can start now — no dependencies
3. **Conversation mode** can start now — no dependencies
4. **Active inference engine** starts after mini model is trained and at least 2 persona prompts exist
5. All merge to main before the EVA-1 demo

## Slide 8 — Training on OpenAI: Step by Step

**Platform:** OpenAI fine-tuning API (no GPU, no infra, fully API-driven)

**Steps:**
1. Export dataset from Supabase: `pnpm ts-node scripts/export-finetune-dataset.ts`
2. Upload: `POST https://api.openai.com/v1/files` with the JSONL file
3. Create job: `POST https://api.openai.com/v1/fine-tuning/jobs` with `model: "gpt-4o-mini-2024-07-18"`
4. Monitor: `GET https://api.openai.com/v1/fine-tuning/jobs/{id}`
5. On completion: note the `fine_tuned_model` ID
6. Update `.env`: `OPENAI_MINI_MODEL_ID=ft:gpt-4o-mini-2024-07-18:marbete-ai::xxxxx`
7. Wire into AIS inference engine Silo 2

**Cost:** ~$3-8 per training run on 300 examples. Negligible.

**Iteration cycle:** Days, not weeks. Can run multiple variants.
